# Porting Axion to Minecraft 26.2

Status: **complete.** `src/compat-26_2` builds, all five guard tasks pass, and
`mc26.2.x` ships as an eighth release range alongside `mc26.1.x`.

**The original premise of this document was wrong and has been rewritten.** It
assumed 26.2 was "a smaller update than 26.1" that Axion could absorb with
mechanical renames in the existing bridge files. Everything below is now
verified against the real 26.2 client jar
(`2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar`) and against a build that
actually resolves and compiles 26.2, not against release notes.

26.2 removes and replaces the entire immediate-mode rendering surface Axion is
built on. That is the port.

## Verified toolchain

Confirmed working — this configuration resolves and reaches the Kotlin compiler.

| | Axion on 26.1 | 26.2 (verified) |
| --- | --- | --- |
| Minecraft | `26.1` .. `26.1.2` | `26.2` |
| Fabric Loader | `0.19.2` | `0.19.3` |
| Fabric API | `0.145.1+26.1` | `0.155.2+26.2` |
| Mod Menu | `18.0.0-beta.1` | `20.0.1` |
| Loom | `1.15.4` (`1.16-SNAPSHOT` for 26.1) | `1.16.3` |
| Gradle | `9.4.0` | `9.4.0` — **no bump needed** |
| Java | 25 | 25 |
| Mappings | official (Mojang), no remap | same |

Two corrections to the earlier draft:

- **Do not bump the Gradle wrapper.** Loom `1.17.x` requires Gradle `9.5.0+`,
  but Loom `1.16.3` builds 26.2 fine on the existing `9.4.0` wrapper. Loom 1.17
  was only wanted for the Enum Extensions API, which Axion does not use. This
  removes the "must revalidate all seven other ranges" risk entirely.
- Mod Menu is at `20.0.1`, not `20.0.0-beta.2`. TerraformersMC Maven was
  returning 502 during this work; `build-axion.sh`'s Modrinth fallback and
  synthetic POM handled it, and that path is what the 26.2 range should use too.

## Confirmed API changes

Verified by `javap` against the 26.2 client jar. The 26.1 column is verified the
same way against the cached 26.1.2 jar.

### Screens, HUD, input

| 26.1 | 26.2 |
| --- | --- |
| `Minecraft.screen` | `Minecraft.gui.screen()` |
| `Minecraft.setScreen(s)` | `Minecraft.gui.setScreen(s)` |
| `net.minecraft.client.gui.Gui` (the HUD) | `net.minecraft.client.gui.Hud` |
| — | `net.minecraft.client.gui.Gui` **still exists, but is now the screen manager** |
| `Minecraft.toastManager` | `Minecraft.gui.toastManager()` |
| `Options.hideGui` | `Minecraft.gui.hud.isHidden()` |
| `Gui.setOverlayMessage` | `Hud.setOverlayMessage` (unchanged signature) |
| `contextualbar.LocatorBarRenderer` | `contextualbar.LocatorBar` |
| `GameRenderer.mainCamera` (field) | `GameRenderer.mainCamera()` (field now private) |
| `Minecraft.mainRenderTarget` | `GameRenderer.mainRenderTarget()` |

**The `setScreen` question from the earlier draft is resolved: both forms exist
and they are not interchangeable.** `Minecraft.setScreenAndShow(s)` is
`gui.setScreen(s)` followed by a forced `renderFrame(false)` — it is the
load/disconnect-boundary variant. For ordinary mod screen switching the correct
replacement is `Minecraft.gui.setScreen(s)`. CrowBar's use of `setScreenAndShow`
is not a counter-example; it is a different call site.

`Gui` keeping its name while changing meaning is the sharpest edge in this
update: `@Mixin(Gui::class)` in `GuiMixin` still compiles and still resolves,
but now targets the wrong class. It must move to `Hud`, whose
`extractItemHotbar(GuiGraphicsExtractor, DeltaTracker)` is unchanged.

### Dyed blocks and items collapsed into `ColorCollection`

The sixteen-constants-per-family pattern is gone:

| 26.1 | 26.2 |
| --- | --- |
| `Blocks.WHITE_WOOL` | `Blocks.WOOL.white()` |
| `Blocks.RED_STAINED_GLASS` | `Blocks.STAINED_GLASS.red()` |
| `Blocks.LIGHT_GRAY_STAINED_GLASS` | `Blocks.STAINED_GLASS.lightGray()` |
| `Items.WHITE_CARPET` | `Items.CARPET.white()` |
| `Items.RED_BED` | `Items.BED.red()` |

`ColorCollection<T>` also offers `pick(DyeColor)`, `asList()` and `map(...)`.
Affected families include `WOOL`, `CARPET`, `STAINED_GLASS`,
`STAINED_GLASS_PANE`, `CONCRETE`, `BED`, `BANNER`, `DYED_TERRACOTTA`,
`GLAZED_TERRACOTTA`, `DYED_SHULKER_BOX`, `DYED_CANDLE`.

`BlockTags.SAPLINGS` no longer exists; only `ItemTags.SAPLINGS` does.

### Rendering — this is the port

`net.minecraft.client.renderer.MultiBufferSource` **and its `BufferSource` inner
class are deleted outright.** So is `ShapeRenderer`. There is no renamed
equivalent. Axion's two load-bearing aliases both point at nothing:

```kotlin
typealias VertexConsumerProvider = net.minecraft.client.renderer.MultiBufferSource
typealias Immediate = net.minecraft.client.renderer.MultiBufferSource.BufferSource
typealias VertexRendering = net.minecraft.client.renderer.ShapeRenderer
```

The replacement is the submit-node system, which existed alongside
`MultiBufferSource` in 26.1 and is now the only path:

```java
// net.minecraft.client.renderer.OrderedSubmitNodeCollector
void submitCustomGeometry(PoseStack, RenderType, CustomGeometryRenderer);
void submitShapeOutline(PoseStack, VoxelShape, RenderType, int, float, boolean);
// CustomGeometryRenderer
void render(PoseStack.Pose, VertexConsumer);
```

This inverts the control flow. Axion's renderers currently pull a consumer
(`consumers.getBuffer(layer)`) and write into it inline; 26.2 wants a callback
submitted against a `RenderType` and replayed later by the engine.

Other renames in the same area:

| 26.1 | 26.2 |
| --- | --- |
| `VertexFormat.Mode` | `com.mojang.blaze3d.PrimitiveTopology` |
| `VertexFormat.IndexType` | `com.mojang.blaze3d.IndexType` |
| `RenderPipeline.UniformDescription` | `BindGroupLayout.UniformDescription` |
| `Builder.withUniform` / `withSampler` | `Builder.withBindGroupLayout(...)` |
| `Builder.withVertexFormat(fmt, mode)` | `withVertexBinding(i, fmt)` + `withPrimitiveTopology(...)` |
| `TextureFormat` | `GpuFormat` |
| `SourceFactor` / `DestFactor` | `BlendFactor` / `BlendOp` |
| `RenderSystem.getModelViewMatrix()` | `RenderSystem.getModelViewMatrixCopy()` |
| `Tesselator`, `VertexMultiConsumer` | removed |
| `RenderType.bufferSize()` | removed; size explicitly (`BIG_BUFFER_SIZE`) |
| `RenderType.mode()` | `RenderType.primitiveTopology()` |
| `MeshData.DrawState.mode()` | `.primitiveTopology()` |
| `RenderPass.setVertexBuffer(i, GpuBuffer)` | `(i, GpuBufferSlice)` |
| `createRenderPass(..., OptionalInt, ...)` | `..., Optional<Vector4fc>, ...` |
| `DynamicUniforms.writeTransform(Matrix4fc, …)` | narrowed to `Matrix4f`, `Vector4f`, `Vector3f` |

Note that `net.minecraft.client.renderer.rendertype.RenderType` and
`RenderTypes` are **not** 26.2 changes — that package move already happened in
26.1.2 and Axion had absorbed it. Only the members above moved.

`Fabric API` renamed its half to match: `WorldRenderEvents` / `WorldRenderContext`
are now `LevelRenderEvents` / `LevelRenderContext` in
`net.fabricmc.fabric.api.client.rendering.v1.level`, and the context exposes
`submitNodeCollector()` + `poseStack()` rather than `consumers()` + `matrixStack()`.
`WorldRenderCompat` resolves these reflectively by name and already listed the
`level.LevelRenderEvents` class and the `poseStack` accessor, but its consumer
lookup only tried `consumers` and `bufferSource` — on 26.2 that would have
thrown at runtime with nothing drawn. It now tries `submitNodeCollector` too.

## The two original risks, resolved

### 1. Raw OpenGL in the GPU preview path — solved, and the fix is clean

`AxionPreviewBlockDrawer` calls `GlStateManager._enablePolygonOffset()` /
`_polygonOffset(-1.0f, -1.0f)`. Under 26.2's switchable, Vulkan-default backend
that is the wrong backend's class.

The replacement is not a Blaze3D call at all — the polygon offset is now pipeline
state. `DepthStencilState` has carried it since 26.1:

```java
DepthStencilState(CompareOp depthTest, boolean writeDepth,
                  float depthBiasScaleFactor, float depthBiasConstant)
```

So the bias travels with the pipeline, is backend-agnostic, and needs no
`try`/`finally` to unwind. Vanilla's `text_polygon_offset` is the reference use.

### 2. Reversed depth buffer — confirmed, with the exact sign

Counted across `RenderPipelines` in both jars:

- 26.1: 15 × `CompareOp.LESS_THAN_OR_EQUAL`, 2 × `EQUAL`
- 26.2: 14 × `CompareOp.GREATER_THAN_OR_EQUAL`, 2 × `EQUAL`

And vanilla's polygon offset flipped sign with it: 26.1's GL
`_polygonOffset(-1.0f, -10.0f)` for text layering is, in 26.2,
`DepthStencilState(GREATER_THAN_OR_EQUAL, true, 1.0f, 10.0f)`.

Two consequences for Axion:

- `AxionPreviewBlockDrawer`'s `(-1.0f, -1.0f)` becomes
  `depthBiasScaleFactor = 1.0f, depthBiasConstant = 1.0f`.
- `VersionCompatImpl`'s preview pipeline uses
  `DepthStencilState(CompareOp.LESS_THAN_OR_EQUAL, false)`. On 26.2 that depth
  test is inverted — the preview would draw only where it is *behind* world
  geometry. This is a silent, compiler-invisible correctness bug, and
  `verifyGpuPreviewCoverage` currently asserts the `LESS_THAN_OR_EQUAL` string
  literal, so the guard would actively defend the wrong value. Both need a
  reversed-Z branch.

### Watch item: custom pipeline shader names — cleared

`assets/minecraft/shaders/core/rendertype_lightning.vsh` and `.fsh` both still
exist in the 26.2 client jar. `createXrayQuadsPipeline()` keeps its shader
names, and the v0.2.11 x-ray selection work is not at risk from the core-shader
reorganisation. `findXrayPipelineSnippet` still needs a 26.2 entry.

## What has been done

1. `src/compat-26_2` created from `src/compat-26_1` (103 files).
2. `build.gradle.kts`: added `rangeMc262x`, plus a shared `rangeMc26x` for the
   things both 26.x ranges want (Java 25, `net.fabricmc.fabric-loom`, official
   namespace with no `mappings` dependency, `jar` instead of `remapJar`). The
   26.1-only lifecycle-events constraint stays 26.1-only. `mc26CompatDir`
   selects the compat source set. Artifact tag `mc26.2.x`, advertised range
   `>=26.2 <26.3`, `src/compat-26_2` added to `allPreviewCompatDirs`.
3. `fabric-server/build.gradle.kts`: the same `startsWith("26.1")` checks
   generalised to `isMc26x`.
4. Verified the build configures, resolves 26.2 and reaches `compileClientKotlin`.
5. **The `MultiBufferSource` replacement**, which was the load-bearing decision.
   Every Axion renderer reaches its vertex consumer through one reflective
   `getBuffer` extension in the compat directory, so the whole inversion is
   absorbed there: `AxionSubmitBufferSource` hands out recording
   `VertexConsumer`s, batches them per `RenderType` in insertion order, and
   replays each batch through `submitCustomGeometry` on flush. Only the eight
   abstract `VertexConsumer` methods are recorded — the interface defaults
   funnel into those after applying their transforms, so what gets replayed is
   already transformed. No renderer changed.
6. `VertexRendering` on 26.2 is deliberately empty. `VertexRenderingCompat`
   reflects for a static `drawOutline` and already had a manual fallback that
   emits the twelve cuboid edges itself; that fallback was dead code behind a
   hardcoded `false`, and now selects itself when no vanilla helper is found.
   It writes into the recording consumer, so outlines still land on the render
   type the caller chose.
7. The depth bias moved onto the pipeline with its sign flipped for reversed-Z,
   and `verifyGpuPreviewCoverage`'s guard was rewritten to defend the pipeline
   form rather than the raw-GL one.
8. Compat bridges for the shared `src/client` code: `setScreen` → `gui.setScreen`,
   `inGameHud` → `gui.hud`, `toastManager` → `gui.toastManager()`, and a
   `MagicSelectIcons` bridge in all eight compat directories for the dyed icons
   and the saplings tag.

`compileClientKotlin` went from 89 errors to 17. 26.1, 1.21.11 and 1.21.5 all
still compile, and every source guard still passes.

## What remains

Nothing at build level. Every range compiles and every guard passes.

One thing cannot be verified from here and must be checked in game:

- **The reversed-Z depth bias sign.** It is derived from vanilla's own
  migration — 26.2 moved text layering from GL `(-1.0f, -10.0f)` to
  `DepthStencilState(GREATER_THAN_OR_EQUAL, true, 1.0f, 10.0f)` and flipped all
  14 of its depth compares in the same update — but a wrong sign shows up only
  as the preview z-fighting with, or vanishing behind, real terrain. No test in
  this repo can catch it.

Also outstanding, and deliberately not guessed at: `run-axion.sh` pins client
mod versions (IAS, Sodium, FerriteCore, Lithium, ImmediatelyFast) by Modrinth
version id per Minecraft version. The retired 26.1 ids were removed rather than
mapped to unverified 26.2 ones; the lookups already degrade with an explicit
"No compatible <mod> release for Minecraft 26.2" message, so the launcher works
without them.

### The `startsWith("26.1")` gates

The 26.1 port left version gates spelled as `minecraftVersion.startsWith("26.1")`
in **three** separate build scripts. Each one silently downgrades 26.2 to the
pre-26 defaults rather than failing loudly:

| file | what it gates |
| --- | --- |
| `build.gradle.kts` | compat source set, Java 25, loom plugin id, `jar` vs `remapJar` |
| `fabric-server/build.gradle.kts` | Java 25, official-namespace deps, no remap |
| `paper-plugin/build.gradle.kts` | Java 25 toolchain, `isSupportedVersion` |

The `paper-plugin` one is the nastiest: paperweight runs `paperclip` on that
toolchain, so a 26.2 build died in `applyPaperclipPatch` with
`"Minecraft 26.1 and newer requires running the server with Java 25 or above"` —
an error about Java, thrown from a Paper task, with nothing pointing at the
version gate. All three are now `startsWith("26.")`.

Worth checking all three whenever a new 26.x lands.

### Two traps worth remembering

Both compile cleanly and fail silently — neither would have been caught by the
build without a deliberate guard:

1. **`@Mixin(Gui::class)`** still resolves on 26.2, because `Gui` still exists —
   it is just the screen manager now instead of the HUD. The mixin binds the
   wrong class, never applies, and leaves the vanilla hotbar drawn underneath
   Axion's. `verifyIntegratedNoClipWiring` now asserts the 26.2 hotbar mixin
   targets `Hud`.
2. **`RenderPass.drawIndexed` was reordered, not extended.** 26.1's
   `(baseVertex, firstIndex, indexCount, instanceCount)` became
   `(indexCount, instanceCount, firstIndex, baseVertex, firstInstance)`.
   Appending a fifth argument to the old call compiles and draws nothing. Both
   call sites now spell their arguments out. `draw` moved the same way:
   `(firstVertex, vertexCount)` → `(vertexCount, instanceCount, firstVertex,
   firstInstance)`.

## Release shape

**A separate `Axion-vX-mc26.2.x.jar` alongside the existing `mc26.1.x` jar** —
eight ranges total. Both are maintained; 26.1 was not retired.

A single jar spanning both is not buildable in any reasonable form. It was
already a bad trade when the only known differences were the `Gui` -> `Hud` and
`LocatorBarRenderer` -> `LocatorBar` class renames; now that 26.2 has deleted
`MultiBufferSource` and `ShapeRenderer` outright and inverted the immediate-mode
control flow, the two ranges do not share a rendering API at all. They keep
separate compat trees.

Advertised ranges:

| range | `depends.minecraft` | compat tree |
| --- | --- | --- |
| `mc26.1.x` | `>=26.1 <=26.1.2` | `src/compat-26_1` |
| `mc26.2.x` | `>=26.2 <26.3` | `src/compat-26_2` |

The 26.2 range is open at the patch level so 26.2.1+ is picked up without a
rebuild, but closed before 26.3 — 26.2 broke this much relative to 26.1, so the
next minor is more likely to break the jar than to run it. Every other range in
this repo is closed the same way. Note that `build-axion.sh`'s
`resolve_metadata_version_range` overrides these values in release builds, so its
entries have to carry the same bounds or the guard is silently lost.

### Shared code carries both

Changes to `src/client` for 26.2 are additive and version-neutral, so the other
seven ranges keep compiling unchanged:

- `adaptConsumers(raw)` is identity in all seven older compat trees and only
  wraps a `SubmitNodeCollector` on 26.2.
- `VertexRenderingCompat` picks its outline path at runtime from whether a
  vanilla static `drawOutline` exists.
- `MagicSelectIcons` gives every range its own spelling for the dyed rule icons
  and the saplings tag.
